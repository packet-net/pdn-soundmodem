# pdn-soundmodem roadmap

Status: current as of 2026-09-17. Describes the open, parked and ruled-out work: the waveform build path, the receive-performance workstreams and the station features Tom has asked for. This is the one living roadmap, and it is the only place open work is tracked; it absorbs the old waveform-roadmap.md, and its receive workstreams come from rx-roadmap.md, whose record is frozen at [archive/rx-roadmap.md](archive/rx-roadmap.md). Several components named here have left this repository and ship from NuGet: ARDOP is M0LTE.Ardop, the OFDM engine M0LTE.Ofdm, the DSP primitives M0LTE.Dsp, Reed-Solomon and LDPC M0LTE.Fec and M0LTE.FecLdpc, IL2P M0LTE.Il2p, POCSAG M0LTE.Pocsag, the FlexRadio client M0LTE.Flex and the FM link model M0LTE.FmChannel. MS110D is still in tree.

## Standing directives

- Proven reliable rather than barely working: bit-exact against an oracle, then the channel models, then a real radio loop before anything is called done.
- Occupied bandwidth never exceeds the reference implementation's, and CI enforces it.
- NinoTNC compatibility is never traded away. New modes are additive, never a reshaping of an existing NinoTNC-compatible mode to suit a different peer.
- Every mode is labelled with the modem or TNC it interoperates with. Candidates rank by: an open spec we can implement from scratch, then guaranteed real-world interop, then packet-data transport over keyboard, beacon or voice modes. See [PROVENANCE.md](../../PROVENANCE.md).
- Anything that changes decode behaviour lands with its sim-ladder A/B and a corpus re-score, and gets a dated entry in [mode-validation.md](mode-validation.md). A mask moves only with a ledger entry that justifies it, and masks come from measured reality, never from aspiration.
- Nothing in the receive work changes a transmitted bit: the parity, QtSM and off-air suites stay the regression gate.

## Delivered

Kept short, because each has its own record. The waveform build order this roadmap used to carry is finished: FreeDV datac OFDM, POCSAG, ARDOP and MS110D App D Phase A and B all shipped in that order.

- **FreeDV datac OFDM** (#4) - all six modes, TX and RX, bit-exact-equivalent to codec2 and interoperating with stock `freedv_data_raw_tx/rx` both directions. Real-path validation came from the production GB7RDG node on 2026-08-15 rather than from the bench procedure: `datac3` 6 of 6 and `datac1` 11 of 14 over an ionospheric hop at 50 W. The written procedure ([archive/freedv-hf-loop.md](archive/freedv-hf-loop.md)) was never run as written and is archived.
- **POCSAG** (paging endpoint and `HEARD` feed) and **ARDOP** (software-complete at ardopcf parity).
- **ARDOP on-air acceptance** (#6), 2026-09-12: an ID frame at quality 99, a ping answered `PINGACK S/N 2 dB quality 90`, a FEC transmission, and an ARQ connection to GB7BPQ (LinBPQ 6.0.25.40) that negotiated to 200 Hz, took a BREAK turnaround, carried 90 bytes and tore down in order. That is the Rung 5 exit criterion of [ardop-design.md](ardop-design.md) 6.2. Procedure in [bench/ardop-on-air.md](bench/ardop-on-air.md). The two gaps it left are closed too: an `ardop` modem's `bandwidth` now caps the negotiated ARQBW (PR #461), and a per-slot busy detector tells the TNC when somebody else is using the slot (PRs #465, #467, off unless the modem entry asks for it).
- **MIL-STD-188-110D App D** (#7) - Phase A and Phase B closed, then the Poor-gate successor program's gate legs G0 to G3 closed on 2026-08-20 with all ten Poor points hard-gated. What is left is hardware and Phase C, below.
- **FlexRadio 6500** (#11) - discovery, session, headless slice, DAX RX and TX, PTT and the band-persistence tune fix all ship, and the live node GB7RDG runs on Flex DAX audio with no sound card in the path. The multi-channel IQ half is still open, below.
- **CM108 mixer, AGC and mic boost** (#17) - PR #416, then dB rather than percent with a state file (PR #419), then the TX gain slider, the input level meter and AGC and mic boost forced off at every start-up (PR #424). The measured receive-level thresholds behind the meter are in [receive-levels.md](receive-levels.md); the start-up ordering rule the work produced (all mixer work finishes before the PCM is opened) is in [CLAUDE.md](../../CLAUDE.md) and pinned by `StartUpOrderTests`, and the 500 ms capture buffer that was the real fix behind it is recorded in [archive/plan-amendment-log.md](archive/plan-amendment-log.md).
- **TX test transmissions** (#18) - PR #415: an operator-page control, `POST /api/txtest` and `--two-tone` / `--tone`, 700+1900 Hz or a single tone with the four FM Bessel-null presets, queued on the channel like a frame and capped at 30 s.
- **More than one modem on one machine** (#19) - PR #477: the `pdn-soundmodem@NAME` template unit, with the `frameLog`, `survey` and `rawCapture` defaults following `$STATE_DIRECTORY` so two instances cannot become two writers on one SQLite file.
- **Per-mode audio centre frequency** (#39) and the **off-air BPSK diagnosis** (#40, #42) - `--modem N:MODE:FREQ` shifts TX and RX together on the AFSK and PSK families and is rejected on the spec-fixed waveforms; the real gap was short-preamble acquisition of an offset carrier rather than a missing differential step, so the default detector is `Differential` (`ModemCatalog.DefaultDetectorFor`) behind a frequency-diversity bank.
- **Receive workstreams** - Watterson masks and the accept discipline, trailer corroboration, ensemble decode-any, the MLSE detector, per-frame SNR in the record, erasure and chase decoding, and timing diversity across every single-carrier mode. The measurements are in [archive/rx-roadmap.md](archive/rx-roadmap.md) and the ledger.

## Open work

### #7 - MIL-STD-188-110D App D: the hardware legs and Phase C

Both remaining gate legs are Tom's hands, and they are the only route by which WN7 and WN8 Poor stop being sim-only: **H1**, a 40 m radio evening (the IQ-versus-DAX A/B, which is built both ways and has never been run as a seeded pair, then the hour-long mixed ladder with power varied), and **H2**, an hour on the studybox rig asking whether the RSP1 pad chain's roughly 13.5 dB deliverable ceiling is set by its gain stages or by thermal noise, with a pad swap if it is the former. +19 and +23 dB sit above both rigs' ceilings as they stand. **Phase C** (32/64/256-QAM, WN9 to WN12, groundwave-gated and high-SNR) has not started. Validation is pdn-to-pdn plus on-air self-consistency, because no external App D oracle exists. Plan and leg definitions: [archive/ms110d/poor-gate-successor-plan.md](archive/ms110d/poor-gate-successor-plan.md).

### #8 - Own FM OFDM

Greenfield speed play through an FM voice channel; VARA FM is the only incumbent and it is closed. Reuses the OFDM engine, now M0LTE.Ofdm. New work is PAPR management, pre-emphasis and de-emphasis EQ, deviation-limit behaviour and sample-clock sync, and it **needs Tom's FM radio loop**, because PAPR, emphasis and deviation cannot be fully simulated. OBW-critical by design. One ceiling is already measured by the FM channel model: a noiseless FM link is not arbitrarily clean, because full deviation on a low tone spreads sidebands past a narrow IF filter and the symmetric truncation comes back as odd-order distortion (third harmonic about -25 dB on an 8 kHz filter), which a dense constellation meets before it meets noise.

### #9 - Own HF OFDM

Narrower HF-SSB OFDM aiming to beat FreeDV datac on throughput and resilience through adaptive bit-loading and pilot/CP tuning, benchmarked head to head against our own datac implementation. Wants the shared engine and the FM work first. Both own modes are labelled `pdn-OFDM`, pdn to pdn only.

### #10 - codec2 LGPL to GPL port licence analysis

A critical reading of the legal basis for the managed codec2 port (LGPL-2.1 to GPL-3.0-or-later via section 3 relicensing) and its attribution (Rowe, Valenti, Cowley). Scheduled by Tom as a roadmap task; not a blocker, and not ours to bless. It needs a real FOSS-licence sanity check.

### #11 - Flex multi-channel IQ receive

The last open half of the Flex work. DAX-IQ is receive-only (there is no IQ TX over DAX), and the front end exists: `src/Packet.SoundModem/Iq/` does concurrent two-channel AFSK decode, and the transport is hardware-validated over M0LTE.Flex's VITA packet event at 238k IQ samples in 2 s with no loss. What is missing is daemon and CLI wiring to select channels and place their offsets. For #8 and #9 later, the only IQ-TX door on a Flex is the SmartSDR Waveform API, which is GPL-3.0 (port it, do not depend on it), runs off-radio on a network host, and was measured on air on 2026-07-18 to give true wideband complex IQ to RF at `underlying_mode=RAW` (both sidebands, 14 to 20 kHz, capped by the 24 kHz waveform rate); USB and IQ modes are SSB-limited. Self-capture during TX is not viable, so OBW stays a bench or second-receiver measurement. Notes: [archive/flex-integration.md](archive/flex-integration.md).

### #12 - 2G ALE in software

MIL-STD-188-141A Appendix A link establishment, so an MS110D station can find a working channel and a listening correspondent unattended. Plan: [plans/ale.md](plans/ale.md). Prompted by the Kenwood TK-90 assessment, whose ALE needs a KPE-2 board that cannot be obtained; doing it in software removes the dependency on any particular radio, makes LQA our own measured SNR rather than a vendor's opaque score, and is a smaller job than the modem already built (8-FSK, no equaliser, no turbo decoder). Unscheduled. One exception is worth taking early: decoding real off-air 2G ALE needs no transmit licence, no partner and no hardware this project does not own, and it would verify the waveform constants empirically.

### Receive performance: what is left

The full measurements, including the nulls, are in [archive/rx-roadmap.md](archive/rx-roadmap.md). What remains open:

- **Full soft Reed-Solomon (GMD/KV)**, still judged diminishing past chase decoding for these block sizes. One cheap idea the chase work suggested: an enumerator that flips adjacent bit PAIRS as single candidates, covering two symbol errors where today's three-flip budget covers one and a half at the same candidate count. It helps payload blocks only, since the header already chases all 4095 subsets of its twelve weakest bits, and payload failures are dominated by the erasure ladder. Sized, not built. This is the one workstream that cannot land from this repository alone: the RS decoder is M0LTE.Fec and the deframer M0LTE.Il2p.
- **Retransmission soft combining**: measured, and the ceiling says do not build. In 28.6 h of real 40 m traffic there were 2 to 5 all-copies-lost retry groups against roughly 1030 decoded frames, a throughput ceiling of 0.2 to 0.4 %, because the link layer's own retransmission diversity is already doing the job at these SNRs. The sizing is one command now (`sm-ota replay --bursts`); re-run it when the corpus contains a storm or contest day, which is the class deep synchronised QSB would populate, and build only if the twins appear.
- **Two-pass, non-causal burst processing.** Sized, recorded, not built: a burst is short and cheap to buffer, so a first pass could estimate its timing, phase and amplitude trajectory end to end and a second pass re-decode against the smoothed estimates. The timing half is a measured null - a perfect clock is worth under 0.1 dB on bpsk300, because the DPLL's inertia is already the smoothing a second pass would be hunting for - so what survives is converged equaliser taps from symbol 0 and fade-envelope erasure flags, and neither pays for the buffering architecture on its own. Converged taps from symbol 0 is also the only route past what the `mlse` detector could not reach causally; the other successor that work named is an A/B of `mlse` on the misses-v2 real audio, where the sim says its gain lives.
- **Channel-model extensions.** Still missing: slow CFO drift plus a 1/f phase process, which is the impairment that walled qpsk2400 (#116) and the RSP1 coherent modes (#102) and is what the undisciplined-radio aspiration needs to develop against; TX/RX sample-clock skew, since real cards sit 50 to 100 ppm apart while the sim shares one clock and quietly flatters every timing loop; SSB passband tilt, QRM injection and AGC dynamics, all waiting on real interferer material; and calibration of the FM ladders against a real radio over the Flex or RSP1 rig, without which an FM mask means no regression against the model rather than a figure about the air.
- **Impulse noise** is modelled, calibrated and costed (an ordinary evening's 120 crashes a minute takes bpsk300 from 88 % to 23 % at AWGN -4 dB), and both fixes tried are measured nulls: a clipping blanker, and crash-marked erasures. The cost is carried by crash TRAINS, an outage class like Poor's flat fades that no in-frame machinery fixes at this wire format. What would pay is avoiding or riding trains (retry timing, the escalation below), not decoding through them.
- **Per-station acquisition priors.** The daemon hears the same handful of stations all day. Cache each one's measured carrier offset, timing skew and level, keyed by heard callsign, and warm-start acquisition from the cache. It targets short supervisory frames, which die in acquisition and are where the real misses skew. Modest scope, measurable directly against a frame log. Not started.
- **Waveform escalation between consenting stations.** The answer to Poor, and to every ceiling above: speak IL2P BPSK as the lingua franca, recognise a pdn-soundmodem peer, and escalate that link to a waveform with the equalisers and interleaving this one lacks. Protocol and node work rather than receiver work. The real-path argument is strong: on 2026-08-15, over the same half hour, power and dial, `datac3` delivered 6 of 6 where `datac1` delivered 11 of 14 and later 10 of 23, roughly 5 dB of link margin bought purely by choosing a different waveform, and the modes it would escalate to are already in the repository and already validated on air.
- **Timing leads.** Every mode issue #331 listed now decides at seven phases. Three leads are left: the 4-PAM clock's wrap can only land on a sample, so its decision instant is up to a tenth of a symbol late and the phase set is not centred on the eye, and reading the decision back to the instant the clock asked for (as `QpskDemodulator` does) is the next cheap thing to measure; TXDELAY costs the C4FSK modes 2 dB on fm-data and 5 dB on AWGN, which is backwards and is bigger than what timing diversity bought them; and the clock hold is only affordable where the zero crossing is resolved, so it is worth revisiting on the direct-FSK chain if that chain ever gets matched-filter timing.
- **Discipline.** The 37-frame corpus is exhausted as a discriminator: do not tune against its tail. New tuning decisions go against the capture campaign's `misses-v2`.

### Daemon follow-ups

- **`POST /api/config?persist=true` still declines on a config file with comments in it**, because it would have to serialise a parsed document over the top of them and delete them, and every real config file on this network has comments in it. The mixer path no longer has that limitation, since it does not touch the config file at all, but the general config API does. The fix when it comes is a surgical edit rather than a round trip: walk the file's bytes with `Utf8JsonReader` (`CommentHandling = Skip`, `AllowTrailingCommas = true`), use `TokenStartIndex` and `BytesConsumed` to find the byte span of the property being changed, splice the new value in at the file's own indentation and line endings, leave every other byte alone, write atomically, and re-read the result through the normal loader before reporting success. Cases to cover: a property present, absent from a section that exists, and a section that does not exist at all; comments before, inside and after the span (the ones inside are lost, and the answer has to say so); trailing commas; braces inside string values; CRLF; BOM; and a file that does not parse, which is refused with nothing written.
- **#33** - the ARDOP host TCP test races on port bind under full-suite load. Harden the test.

## Parked

Tom's requests, recorded with the decisions taken at the time, none of them for now.

### #13 - A second Flex slice, receive only, on another band (2026-09-04)

Tom: "I'd like the ability for pdn-soundmodem's flex support to be able to create a second slice, so that for example it could listen to 20m packet as well as being a transceiver on 40m packet." The shape when it comes: the daemon opens a second headless slice on its own DAX channel (the 6500 has four of each), receive only, and runs a second `Station` over it with its own modems, frame log and waterfall page, which the `Station` extraction of the monitor work makes a wiring job rather than a rewrite. The 40 m slice keeps PTT and the KISS host; the second slice never transmits. Config shape to decide then: a second `device: flex:<radio>:<slice>` entry with its own `modems`, or a `listen` block beside the main one. A listening slice is a station the public monitor could show ([archive/uplink-plan.md](archive/uplink-plan.md)). Known constraint from the IQ work: a second slice cannot self-capture during TX, so the two bands are independent receivers only while the first is not keyed.

### #14 - Audio record button with lookback, from a ring buffer (2026-09-04)

Tom: "an audio record button, working from a ring buffer so when I press record, it immediately snapshots the ring buffer's contents, starts recording, and prompts me how many seconds back it wants to keep. Then, when I press stop, the whole of the chosen lookback + all of the audio to the point of the stop button being pressed is handed to the user." Decisions taken with the request: the ring must not add a persistent stream to any UberSDR receiver, so no viewers connected means no session and no ring; it fills only while the station is live for a viewer, and the lookback on offer is whatever has accumulated since the session opened, up to the ring length. The button is on the public page. One recording open per user at a time; each viewer may have their own take on the same station, but not two. Our own transmitted audio is included when the station is a transceiver, filling the gaps the receiver blanks during TX, so the take is what the station was working rather than only what it heard. The shape when it comes: the ring lives in the daemon, not the page, so the lookback covers time before this viewer pressed Listen; it holds the same receive feed the Listen button gets (mono s16 at the station's sample rate, so five minutes is about 7 MB at 12 kHz and 29 MB at 48 kHz), one ring per `Station`, allocated when the session opens and dropped when it closes, length from config (`record.ringSeconds`, default to decide). Record snapshots the whole ring at once and starts appending live audio, and only then does the page ask how many seconds back to keep, so nothing is lost while the prompt is open; the answer is capped at what the ring holds and trims the snapshot's front. Stop closes the take and the page fetches it as a WAV, served once and then dropped, named with the station, dial and UTC start time. A cap on take length is needed on a public page, value to decide then, and since takes are per viewer the cap also bounds what a page full of viewers can hold open.

### #15 - Full duplex using UberSDR as remote receivers (2026-09-04)

Tom: "Full duplex using UberSDR as remote receiver(s)." The station transmits on its own radio and receives through one or more public UberSDR receivers at the same time, over the `ubersdr:` input that already exists. A remote receiver is not blanked by the local transmitter, so the station keeps hearing the channel while it is keyed: it can hear its own signal as others hear it, hear a collision as it happens, and with several receivers pick the best copy of the far station from several sites. The shape when it comes: `device` stays the transmit radio, and a `receivers` list of `ubersdr:<host>` entries each becomes a receive-only `Station` sharing the node's modems and frame log, with one vote per frame across the local receiver and the remote ones. Constraints to measure first: the round trip of a remote receiver's IQ path against AX.25 turnaround timing, since the node's reply timing and the far end's T1 both assume it heard promptly; the receivers' per-address daily allowance, which a node keyed all day would use up; and which receiver's dial the modems are planned against when they disagree by a few Hz. A station whose receiver is an UberSDR may not publish to the public site ([archive/uplink-plan.md](archive/uplink-plan.md) decision 7), and this feature is the case that decision was protecting.

### #16 - Flex ATU on and off from the daemon (2026-09-05)

Tom: "ability to turn flex ATU on/off." An operator control, never a public one, that puts the 6500's internal tuner into bypass or back into use and on request starts a tune, over the command session the Flex client already holds. The SmartSDR commands are `atu bypass`, `atu start` and `atu clear`, with `atu set memories_enabled=0|1`, and the outcome arrives on the `atu` status object (`status=TUNE_BYPASS|TUNE_IN_PROGRESS|TUNE_SUCCESSFUL|TUNE_FAIL|...`, `atu_enabled`, `memories_enabled`, `using_mem`); confirm the strings against the flexclient source as the rest of the Flex work did. Three places it could be driven from, to pick then: a `flex.atu` config setting applied at bring-up (bypass, in use, or leave the radio as found, the last being today's behaviour and the safe default), the config API for a change while running, and a control beside the radio status on the operator page. A tune keys the transmitter with a carrier, so starting one is always the operator's act, never something the daemon does by itself; bypass and un-bypass do not transmit. The `radio` status line should show whether the tuner is in or out, and the journal should say what was asked and what the radio answered, in ASCII. The tuner is per radio rather than per slice, so with #13 a tune on one slice's band affects both. Needs the radio on the bench and a load or the antenna.

### Modes parked or noted

- **M17** (open 4FSK plus Codec2 voice, native KISS packet mode) surfaced strongly in the mode survey and is a good fit next to our C4FSK experience, but is parked (Tom, 2026-07-16, "leave it out for now"). A deferred candidate, not on the build path.
- **The WSJT-X family** (FT8, FT4, JS8, MSK144, Q65) is open but a poor packet-data fit, with tiny fixed-format payloads. **MT63, Olivia, PSK31 and RTTY** are fldigi-lineage keyboard modes, cheap but chat-oriented, needing the separate flmsg or flamp layer to carry data. Noted, not planned.
- **FreeDV voice coexistence** is a non-goal: data and voice never share a channel.

## Cannot implement

Proprietary or blocked, with the reason, so the question does not get re-asked.

- **VARA HF and VARA FM** - closed shareware, and the licence forbids reverse engineering. VARA FM, about 25 kbps through an FM voice channel, is the benchmark our own FM OFDM aims at, but there is nothing open to adopt.
- **PACTOR II, III and IV** - closed; PACTOR-4 is SCS P4dragon hardware only.
- **P25, NXDN and dPMR** - AMBE-family proprietary vocoder, gated specs, and next to no ham relevance.
- **System Fusion and C4FM (Yaesu)** - no public spec at all, only MMDVM reverse engineering, which fails the rule about not taking an implementation as the spec.
- **FLEX paging** - reverse-engineered rather than openly specified, a GPL-incompatible encoder, and no live ham network. Prefer POCSAG and DAPNET.

For **DMR and D-STAR** the modulation and framing layers are open and only the voice payload is AMBE-blocked, so a data-only variant is not blocked by anyone's IP. Low ham value; noted, not planned.

## Already covered: label, do not build

- **APRS** is the existing AFSK 1200 (Bell 202) and 9600 GFSK.
- **CubeSat 9600 G3RUH telemetry** is the existing GFSK 9600, the same scrambler, AX.25 and KISS. Only Doppler tolerance is an open operational question.

## Needs Tom and a radio

None of these is blocking, and each is self-contained. Operate as M0LTE.

1. **The MS110D radio evening and the pad-chain hour** (#7, legs H1 and H2). The highest-payoff hardware time on this list: H2 is the only route by which WN7 and WN8 Poor become rig-confirmed rather than sim-only.
2. **An FM radio loop** (#8), when the build starts, to validate PAPR, pre-emphasis and deviation, which simulation cannot capture.
3. **The mixer and TX-test bench items** (#17, #18) - the TX gain slider heard on a real transmission, the input level meter read against a real signal on the air rather than a generated tone, a card that has a Mic Boost control to be switched off, a CM108 unplugged while the daemon holds its mixer open, a real Bessel null at the four tones, and a 30 s key-down into a real PA.
4. **One ALSA start-up on a card other than the bench CM108** (#17). The 500 ms capture buffer and the new recovery path change how every ALSA station opens its capture stream, and only the bench CM108 has proven them; the live node is a Flex and never exercises that code. The fallback path for a card that refuses the request has never run at all.
5. **An FM ladder against a real radio**, to tie the FM channel model's knees to hardware; until it runs, an FM mask means no regression against the model.
6. **The CM108 unkey, on a scope, on radio1.** `Cm108Ptt` had its two GPIO report bytes the wrong way round from the day it was written until 2026-09-17: data and the data-direction register are the other way about in the C-Media layout that Hamlib quotes and Dire Wolf sends. A keyup is symmetric in the two orderings, so the fault could only ever show on the release, where writing the direction register as 0 turns the pin into an input and lets it float instead of driving it low. On a board with no gate pull-down, which the CM108 Radio Widget is, that is a transmitter released by leakage or not at all. The bytes are now right and `Cm108PttTests` pins them, but nobody has watched the pin: what is wanted is a scope or a meter on GPIO3 across a keyup and an unkey, and the answer to whether the old ordering was in fact holding the radio up. The same trip settles the browser path below.
7. **The browser station on one USB lead** (`web/`). `Cm108Ptt` in the npm package keys a CM108 over WebHID, so a tab can drive a dongle that carries receive audio, transmit audio and PTT with nothing else plugged in. Chromium's protected-usage list (`IsAlwaysProtected`, services/device/public/cpp/hid/hid_report_utils.cc) covers the keyboard page and the Generic Desktop pointer, keypad and system ranges and reaches no part of a CM108, so this should simply work, but no dongle has been in front of it. Three things to find out, all in one session with the demo page and a dongle: whether the device appears in Chrome's picker at all (which settles the report descriptor, the one thing not confirmed from documentation), whether `TAG+="uaccess"` is the udev rule a browser needs rather than the daemon's group rule, and what the PTT-to-audio alignment looks like when the keying is HID rather than serial. The console trace prints every report byte for byte, and the page now carries the RX and TX level sliders and the TX test, so the same session can settle the levels off the meter and read the alignment off a steady two-tone burst rather than off packet bursts going past.

Hardware available: a Flex 6500 (10.45.0.76, on the bench with an ANT1 dummy load, into which GB7RDG's transceiver couples), GB7RDG's HF port, radio1 (a Pi with a CM108 and a radio on a dummy load), and an FM radio loop.
