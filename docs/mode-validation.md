# pdn-soundmodem - mode validation report and provenance ledger

Living document. Tracks every mode string accepted by `ModemCatalog` (`src/Packet.SoundModem/Modems/ModemCatalog.cs`), how each has been validated (simulation and over-the-air), and - the point of this file - a dated, append-only ledger of *who/what proved a mode working*, with special attention to modes that were **broken and later fixed**, so a regression can always be traced back to the evidence that closed it the first time.

## Purpose and maintenance rule

This file exists because "does mode X work" is otherwise answered by grepping commit messages and hoping. Two things must stay true as the project moves:

1. **Every mode string in `ModemCatalog.KnownModes` appears in the matrix below**, with its current status. When a mode is added, removed, or renamed in the catalog, this file changes in the same PR (mirrors the `docs/plan.md` discipline).
2. **Every time a mode's validation status changes - especially broken → fixed, or working → regressed - append a dated entry to the [Validation ledger](#validation-ledger)** citing the exact commit hash, PR number, and/or issue number that did it, plus the evidence (mask figures, corpus decode counts, on-air BER). Do not edit or delete a prior ledger entry to "correct" it in place; append a new one and let the old one stand as the historical record. Where the provenance is genuinely not known, write **TBD** - never invent a commit, PR, or issue number.

Status legend used in the matrix:

- **working** - validated both in simulation/interop and confirmed over real RF (or, for corpus-based checks, against a real captured off-air/rig recording).
- **partial** - validated in simulation, but the on-air/interop result is mixed, marginal, or has a known open issue against it.
- **untested** - no meaningful validation recorded beyond the mode constructing (`ModemCatalog.Create` succeeding), or coverage is too thin to call it exercised.
- **not-yet-on-air** - solid simulation/interop validation; no real-RF attempt has been made yet.

- **2026-08-01 - backtracking deframer shipped (M0LTE.Il2p 0.1.2); c4fsk energy-gate removal attempted, measured, and retreated.** Toward closing the C4FSK acquisition-floor gap vs the NinoTNC (our 10-20 ms is the energy gate's assert latency; theirs is one 16-bit word), the deframer was made **backtracking**: every physical bit lands in a 16 KB ring, and any failed collection (header RS, body RS, CRC) rewinds the read cursor to one bit past the failed sync and re-hunts - bit-for-bit equivalent to never having false-locked, so a real frame swallowed by a garbage collection is always recovered (a 23-bit hunt warm-up after register clears guarantees termination). - **2026-08-02 (later still) - the 300 AFSK bank's reported frequency offset was a branch index, not a measurement; it is now a measurement, to ~2 Hz.** Building the ID-beacon ghosts on `afsk300` put the bank's `FrequencyOffsetHz` onto the waterfall for a second kind of frame, and probing it across the bank showed it was not a frequency at all. `Afsk300MultiModem` emitted the *first* branch to complete a frame and feeds branches in ascending order, so what reached the display was the lowest-centred branch that could still copy the signal - measured: true 0 → **−105**, true −140 and −70 → **−175** (clamped at the bottom branch), true +140 → +35, and the value moved with buffer framing (the same on-frequency signal read −35 through the daemon's device-sized blocks and −105 through one large buffer). Fine for deciding *whether* to emit, since the deduper is content-based and the bytes are identical whichever branch wins; wrong as the number an operator tunes by. #191's own test recorded the weakness honestly ("a lower bound on the true offset, not a measurement") rather than overclaiming - this replaces the weak contract with a real one.
  **The measurement was already being computed and thrown away.** The slicer's threshold is the midpoint of the mark and space envelopes, which is the discriminator's DC level, which is the carrier offset: summing the two tones cancels the ±shift and leaves `sin(4π·offset/rate)·cos(4π·shift/rate)`. `AfskDemodulator.CarrierOffsetHz` inverts that - no new filter, no per-sample cost, and derived from the same envelopes the bit decisions come from, so a frame that decoded has a settled reading by construction. Min/max envelopes rather than a mean is what makes it survive an HDLC preamble's 87.5 % mark duty cycle. Two things fell out of the probing: the chain mixes I from the sine and Q from the cosine (the transpose of the usual convention), so **the discriminator runs downward as frequency runs up** and the reading needed negating - never noticed before because the sign only picks which tone is mark, and mark assignment is free here (NRZI is polarity-agnostic; both IL2P receivers hunt sync in both polarities). And the reading compresses beyond ~±40 Hz where the discriminator clamp truncates the outer peak (±53 reads ±45, ±70 reads ±53), staying monotonic, which is all the branch ranking needs.
  `Afsk300MultiModem` now holds every branch's copy to the end of its chunk and emits the one with the smallest measured residual - the best-matched branch, which with 35 Hz spacing is never more than half a step out and so always reads in the honest zone; `branch + residual` is the answer. Cost: a frame waits up to 100 ms (one dedupe chunk) against frames that take seconds at 300 baud. **Measured after: −160 → −158.0, −140 → −138.5, −105 → −103.4, −70 → −68.5, −35 → −33.4, −17 → −15.9, 0 → +1.5, +17 → +18.0, +35 → +36.6, +70 → +71.5, +105 → +106.5, +140 → +141.5, +160 → +161.1** - worst error ~2 Hz across ±160 Hz, against up to 105 Hz before, and correct even at the two half-step points where no branch is "the" branch. A residual ~1.5 Hz bias is left uncharacterised; it is 0.5 % of the baud rate and below what any tuning decision turns on. `Afsk300MultiModemTests.The_Reported_Offset_Is_A_Measurement_Of_The_Signal` pins all thirteen points (a return to naming branches would show up as a ~35 Hz step); a lone `Afsk300Modem`, which reported no offset at all before, now reports one too. - **2026-08-04 - the BPSK bank's reported frequency offset was a branch index too; it is now a measurement, to well under 1 Hz.** The same defect the 300 AFSK bank had (2026-08-02, above), in `BpskMultiModem`, found by Tom in the live frame log rather than by a test: 26 hours of the GB7RDG 40 m channel (Flex 6500, GPSDO-locked, `bpsk300` at 7.051600 MHz) produced 431 frames whose `offset_hz` took **nine distinct values and nothing else** - the 4 pairs × 7.5 Hz comb itself - with **354 of 431 (82 %) reading exactly −30 Hz**, the most negative branch. `EI0RSI-1` read +30, then −30 eight seconds later, then −15, inside 23 seconds; no carrier moves 60 Hz in 8 seconds. On a GPSDO-locked rig it looks exactly like a channel mistuned by 30-odd Hz, and was diagnosed as one before anybody read the source (**issue #202**).
  **The measurement was, again, already being computed and thrown away.** The differential detector forms z·conj(z one symbol ago) and takes its *real* part as the bit decision; the imaginary part it discards is the carrier's per-symbol rotation. Squaring the normalised product strips the 0-or-π data step - for random payload and for the all-reversal training preamble alike - leaving a phasor at twice the offset, which is exactly `BpskCarrierOffsetEstimator`'s algorithm; it is now inlined into `BpskDemodulator.CarrierOffsetHz` at the cost of a `sqrt` and a handful of multiplies per sample, against the two transcendentals the mixer was already spending. One difference from the standalone estimator, and it matters: that class peak-holds since its last reset, which would freeze on the first strong burst of a 26-hour session, so this windows the recent signal (~1000 contributing samples) and a frame's reading describes *that* frame. Unambiguous over ±baud/4 - ±75 Hz at 300 Bd, far wider than any bank span. The coherent path needs none of this: its Costas NCO is already tracking the carrier, so the loop's own frequency correction is the residual, gated on DCD.

- **2026-08-08 (later6) - the qpsk3600 high-signal anomaly is explained: a non-integer 6.667 samples per symbol, with QtSoundModem showing both the mechanism and the fix.** Tom pointed at the QtSoundModem source (GPLv3, the sanctioned cross-check per CLAUDE.md). Its `ax25_demod.c` settles it. **QtSoundModem never lets its symbol sampler see a fractional samples-per-symbol ratio**: `make_core_INTR` interpolates each PSK mode by `n_INTR = baud/300` - **6 for SPEED_Q3600** - and `decode_stream_QPSK` then hardcodes `baudrate = 300`, so every PSK mode reaches the decision point at exactly 40 samples per symbol. Its sampler is a different design from ours as well: an exponentially averaged envelope per position-within-symbol (`bit_buf[sample_cnt]`, 0.95/0.05) whose peak position selects the decision sample, an estimator that *improves* as noise falls - the opposite of what we measured. Our `qpsk3600` runs natively at 12 kHz, i.e. **6.667 samples per symbol**, and it is the only catalogue mode with a non-integer ratio; `qpsk600` (40), `qpsk2400` (10) and `bpsk300` (40) are integers and are exactly the modes that show no effect. **Confirmed by direct measurement** (AWGN +40 dB, N=30): 28/30 at 12 kHz (6.667 sps), 29/30 at 10.8 kHz (6.000), **30/30 at 36 kHz (20.000)**; and on the FM path where the effect is severe, 20 samples/symbol removes it entirely - **30/30 at both +24 and +40 dB CNR against 26/30 and 21/30 at 6.667**. **The fix must be internal interpolation in the receive path, not a catalogue rate change**: no divisor of the 48 kHz soundcard rate yields an integer samples-per-symbol at 1800 baud (48000/1800 = 26.667), which is presumably why the mode sits at 12 kHz. Interpolating by 3 (20 sps) or 6 (40 sps, matching QtSoundModem) inside `QpskDemodulator` is the change; **not built, and no mask moves until it is**. Recorded because it is operationally real: a strong local signal is the normal case for FM packet, so this is the regime the mode is most used in, and the mode was validated at 30/30 on clean audio in the QPSK campaign precisely because that campaign never measured it above +18 dB.

- **2026-08-09 (later) - the FM channel model had a rate-dependent defect: its filters are specified in hertz now, every FM mask was re-measured through the fix, and none of them moved.** `FmChannel` was extracted to the public `M0LTE.FmChannel` package (#274) so this repository and the private OFDM one share one definition rather than a copy; the extraction found the defect and 0.3.0 fixes it. **Every filter in the model used a fixed tap count.** A windowed-sinc's transition width is roughly `rate/taps`, so a fixed count makes a filter twice as sloppy each time the sample rate doubles - which is not how a radio behaves, its audio filters being analogue and no wider because a sound card samples faster. The consequence was that the same waveform measured at two sample rates went through two different channels, with the higher rate penalised, so no measurement at one rate could honestly be compared with one at another: a bad property in an instrument whose entire job is comparison. Filters are now specified by shape and the tap count derived at whatever rate the stage runs at, across all four rate-dependent stages (IF filter, audio band limit, and both resampler anti-alias filters; the flutter generator's own filter already ran at a fixed low rate of its own). For a 300-3000 Hz microphone path that is 119 taps at 12 kHz where it was 127, 239 at 24 kHz and 475 at 48 kHz - the 12 kHz case barely moving is the shape you want, the sharpness being the same in hertz everywhere instead of accidentally best at the lowest rate. **Measured on the audio-band OFDM waveform**, 16 seeds a rung: before, 24 kHz scored 16/16/16/16/14/4/0 against 48 kHz 16/16/16/16/13/4/0 across +28 down to +10 dB CNR; after, 24 kHz 16/16/16/16/14/2/0 against 48 kHz 16/16/16/16/13/2/0. That is the outcome worth recording rather than a set of new numbers: the modes most exposed to the change are the 48 kHz ones (`fsk9600-il2p`, `c4fsk9600`, `c4fsk19200`), and they were unaffected. The masks are still the model's own numbers, so nothing here moves any mode toward on-air validation. **One instrument sensitivity found and left alone, because it is faithful rather than wrong**: the model calibrates drive from the burst's own peak, the way a bench does, so a waveform's peak-to-average ratio feeds back into its effective deviation and two bursts of different length or content are not driven identically. It is real behaviour, but it means a code-rate A/B on a single burst length is not a clean single-variable comparison, and it explained a puzzling 8-of-8 acquisition failure in the OFDM ladder that had nothing to do with the receiver.

- **2026-08-09 (later2) - OFDM-FM's channel estimate is denoised, and two plausible improvements measured nothing and were reverted.** In `packet-net/pdn-ofdm-fm`, recorded here because the negative results are the durable part and the private repository's `docs/receiver-findings.md` carries the detail. **What landed**: the preamble-derived channel estimate is one noisy division per carrier and it is that receiver's dominant impairment, since equalisation divides by it and the waveform always has carriers 20 dB down on the edges of a voice passband. The estimate is transformed to a delay profile, each tap shrunk by how much of it is signal rather than noise, and transformed back - the channel being a handful of filters, its energy sits in a short run of delays, while noise is spread over all of them. Measured 8 seeds through the FM link, both legs through FmChannel 0.3.0: uncoded 8/8/7/2/0/0 -> 8/8/8/5/0/0, rate 2/3 8/8/8/8/8/3 -> 8/8/8/8/8/7, rate 3/4 8/8/8/8/3/0 -> 8/8/8/8/7/0 across +40 to +16 dB CNR, with no rung going backwards. Two details are load-bearing and both were got wrong first: it must transform the occupied bins only (inventing values for the unoccupied ones rings, and rang hard enough to break QAM-256 on a *noiseless* loopback while QPSK never noticed), and the bulk delay must be removed before the transform and restored after (the burst is not sampled where the channel's response peaks, so the estimate carries a phase ramp of non-integer slope, and a non-integer ramp does not transform to a spike - it transforms to a sinc smeared over every tap, at which point the shrinkage eats the channel; it showed as a loss at *high* CNR, where there is nothing to denoise and only the distortion is visible). **What did not land, both built and measured before being reverted.** *Decision-directed estimation*: when a payload fails its CRC, slice every equalised carrier of every symbol to its nearest constellation point, average the residual over all of them (pilots free, being known exactly), fold it into the estimate and decode again - in principle beating a single-symbol preamble estimate by roughly the square root of the number of symbols. It won **0 of about 30 attempts**, across the plain ladder and a flutter ladder at 2, 5, 10 and 20 Hz Doppler; by the time a payload fails it is not marginally wrong, so slicing gives a reference too corrupt to help, and the cases a better estimate would have rescued are already taken by the denoiser, which is cheaper and runs on every burst. *Lowering the sync threshold*: the whole rate 3/4 rung at +16 dB was failing acquisition outright (worst normalised correlation 0.695 against a 0.8 threshold), which makes the threshold look like the binding constraint - but sweeping it to 0.6, 0.45 and 0.3 changes the ladder in **no cell at all**, acquisition succeeding and the payload failing instead. It was masking the failure, not causing it. **The finding worth acting on next** is the failure budget under flutter, counted by the stage that lost each frame: at 20 Hz Doppler and +20 dB CNR, of 14 lost frames **7 are the header**, 4 sync and 3 payload. The header is the only part of the burst with no coding on it - 40 uncoded bits, hard sliced, behind their own CRC - while the payload underneath survives conditions it does not. That is a waveform change rather than a receiver one, and it is now the largest single lever. **Still not proven, unchanged from the entry above: no OFDM-FM mode has masks in either tier and none of it has been on the air.**

- **2026-08-09 (later3) - OFDM-FM's header is coded and spread over two symbols, and the fix was decided by measuring the header on its own rather than by reasoning about it.** In `packet-net/pdn-ofdm-fm`; recorded here because the method is the transferable part. The entry above named the uncoded header as the largest single cause of lost frames on a fading link and called it the next lever. It was, but **not for the reason the name suggests**, and the instrument that settled it is the point: a header ladder that hands the receiver the sync position and counts headers read correctly out of bursts actually acquired, so acquisition and payload cannot contaminate the number. Measured that way the old header read **64 of 64 at every carrier-to-noise ratio where the burst could be acquired at all with the flutter off**, and 18 of 40 at +20 dB with 20 Hz of Doppler. It was never noise limited; it was fade limited. The flutter is a flat fade on the RF carrier, so all 110 carriers go down together, and a header living inside one symbol has no diversity of any kind to exploit when that symbol is in a fade - no code, however strong, changes that. What a fading channel pays for is diversity order, and the only axis with any left is time. **So the header is now tail-biting convolutional K=9 at rate 1/2 (40 bits in, 80 out), soft-decision Viterbi, laid across TWO header symbols** by a stride coprime to the coded length so every coded bit appears in both. The sizing was done before building: adjacent symbols are 45 ms apart at this geometry and the model's Gaussian Doppler shaping puts the fade correlation between them at 0.13 at 20 Hz, 0.60 at 10 Hz and 0.88 at 5 Hz, so the diversity lands where the header was broken and is barely needed at 5 Hz where it already read 44 of 46. Two details are load-bearing: the soft metric weights each carrier by `|H|^2` as before **and now each symbol by its own pilot-measured amplitude** (two symbols carrying copies of a bit are two different fades, and without that the faded one gets equal say and most of the second copy's value is discarded), and the bit-to-slot mapping walks all header symbols as one run of slots rather than assuming exactly two - the first version left most of the code untransmitted on profiles narrow enough to need three. **Measured end to end**, flutter failure budget, same instrument and seeds both legs, every burst counted once in the stage that lost it: at 20 Hz Doppler, +20 dB CNR **2/16 recovered becomes 8/16** (header bucket 7 -> 3), +24 dB 8/16 -> 12/16, +28 dB 13/16 -> 16/16; at 10 Hz +20 dB 7/16 -> 9/16; at 2 Hz +20 dB 10/16 -> 13/16. Over all twelve cells **134 frames recovered becomes 155 and the header bucket falls from 16 to 6**. The payload bucket falls too, 25 to 16, which is not a payload change but the consequence of ordered buckets: bursts that used to die at the header now reach a payload that is coded and interleaved over ten symbols and was always the more robust half, so a fragile header had been discarding bursts that were perfectly decodable underneath it. **Costs**: one extra symbol on every burst, which on the plain non-fading ladder shows as the uncoded row losing two frames at +24 dB and rate 2/3 gaining one at +16 - the channel model calibrating drive from the burst's own peak the way a bench does, so a longer burst has a higher expected peak and marginally less average deviation. **Two tests were passing for the wrong reason and are fixed rather than deleted**: both claimed to wreck samples "past preamble and header, into the payload symbols" and both computed that offset as a hand-counted symbol index which was in fact the header symbol; they passed because wrecking the old header killed the burst, and the fault only became visible because the new header survives one wrecked symbol, which is exactly what it is for. **What this does not settle**: sync is now the largest bucket (15 lost frames against the header's 6) and the recorded threshold sweep warns that acquisition failures at the bottom rung were masking payload failures rather than causing them, so that is the next leg and it needs its own instrument first. **Still not proven, unchanged: no OFDM-FM mode has masks in either tier and none of it has been on the air.** Worth stating plainly for anyone reading the Doppler figures: the axis is Doppler *spread*, not Doppler *shift* - a carrier offset is irrelevant to an FM link, which turns it into a DC offset well below the waveform's lowest subcarrier at 305 Hz. What is being modelled is mobile flutter, the rate at which a moving station's multipath pattern sweeps past, `v/lambda`: 6.3 Hz for 13 m/s at 145 MHz and 19 Hz at 433 MHz, 14.5 and 43 Hz at 30 m/s. So the rows that were broken are a station driving, and the 0 Hz row - fixed antennas, base to base - is precisely where the old header was already perfect.

- **2026-08-09 (later5) - a second and larger correction to the header entries above: the coding was the whole win and the time diversity was worth nothing, which two dated entries got backwards.** Tom, reading the write-up: "I highly doubt that this modem will ever be used for mobile operation tbh. - **2026-08-11 - OFDM-FM negotiates its own rate, and the measurement campaign behind it says eleven of the 24 rates a header can name should never be sent.** In `packet-net/pdn-ofdm-fm`; here because the method and the negative results are the transferable part, and the "no matrix row for OFDM-FM" rule from 2026-08-09 stands. **What the wire gained.** The header already named the constellation and a receiver already used it, so one end could follow another from BPSK to QAM-256; the *coding* was not named, so the receiver decoded with whatever its own configuration said and both ends had to be set alike in advance, a mismatch looking exactly like a bad path. The coding index cost nothing: the length field was 20 bits and validated at 65535, so four of them could never be set. A recommendation for what a station would like to **hear back** cost 8 more, and the header is still one symbol on every real profile, so the whole of negotiation costs no air time at all. The change that mattered was not the bits but the burst sizing: a streaming receiver works out how long a burst is from its header before it has the burst, and sized from its own configuration rather than the signalled one it stops collecting part way through and hunts for sync inside the remainder. **The ladder, measured not derived** (`RateLadderGridProbe`, R1/T13 on a TM8100 narrow at 2500 Hz, 256-byte payload, K=9, coarse at 16 seeds to bracket each cliff then 64 on 1 dB steps): of the 24 constellation-by-coding combinations, **thirteen survive and eleven are dominated** - for each of those there is another rate at least as fast that also needs less signal, so a scheme able to select one eventually will and will then be slower AND less robust at once. Two results nobody would have guessed. **Rate 2/3 owns the top of the ladder**: every rung above QAM-16 3/4 is a 2/3 code, so the obvious design of one code rate with the constellation varying misses most of the range. **QAM-128 is dominated at all three code rates**, because a burst is a whole number of symbols and seven bits per carrier usually rounds up to the same symbol count as eight - it pays QAM-256's noise penalty for QAM-64's air time. Payload size is not a detail either: at 64 bytes the same rounding merges whole groups of rungs and the ordering does not hold. The surviving ladder spans 17.1 dB for 5.2x the throughput. **The margin measure**: re-encode what the Viterbi decoder decided, compare against the demodulator's own hard decisions, and the difference is how much of the code's correcting power that burst spent. It rises smoothly as signal falls, where "the CRC passed" is one bit that arrives too late, and **the value at which a rate gives out is a property of the code rate and not the constellation** - about 0.09 at rate 1/2, 0.05 at 2/3, 0.03 at 3/4 - so a station needs three numbers rather than thirteen. It also has a measurement floor that shaped the policy: an error rate is a count over a few thousand coded bits, good to about 8 % at the cliff and to about 45 % at 3 dB of margin, so it is sharp exactly where a station is in trouble and vague exactly where it has room. **The policy, and the two wrong diagnoses on the way to it.** Closed against an oracle - every fixed rate over the same link and seeds, best taken afterwards, air time counted for failed bursts too - the first version reached 72 to 91 %. I blamed the step-up rule for wanting a *run* of consecutive clean bursts (real, worth about 3 points) and then blamed using one slope for how fast the error rate falls with signal (also real - 0.36 per dB on BPSK against 0.81 on QAM-256, so one fitted 0.7 reads anything from 2.4 to 11.3 dB where the truth is 4.0 - and also worth about 3 points). Neither explained the gap. **Counting the retreats instead of theorising about them found it in ten minutes**: at +16 dB, zero retreats on failures and fourteen on bursts that had decoded perfectly. Stepping down whenever one successful burst looked expensive was the whole fault. A burst that decoded is proof the rate works, whatever it spent getting there. What replaced it is the durable part: **choose the rung with the best expected THROUGHPUT, not the best margin** - translate the current rung's margin to every other rung through the difference in their cliffs and each rate's own slope, turn the implied spending into an expected frame success, multiply by goodput. A rate losing one frame in seven at 4107 bit/s is well ahead of one losing none at 3227, and deciding on margin alone always picks the safest rate. Final: **87 to 93 % of an oracle that knew the answer in advance**, settling on the right rung at three of five signal levels. **Wired into the modem**, where three more things were needed that the component did not have: a burst reported once rather than once per retry attempt (a failed payload is retried a sample on, so one wrecked burst otherwise reads as a run of failures); opening at the configured rate rather than the bottom of the ladder (the first burst of any link goes out before anything is heard back); and expiring a recommendation after two minutes, which took a `TimeProvider` and whose fake clock immediately found a real bug - the "have I heard anything" sentinel was a zero timestamp, which a real clock never returns and a test clock always starts at. **Off by default, and not for compatibility.** Two of the three situations it can be in are ones it makes worse: a beacon or one-way link never hears anything back and sits where it started, and on a shared channel several correspondents' reports average into one nonsense recommendation, because the payload here is an opaque AX.25 frame and this layer never reads an address. It is right for a point-to-point link. **Still not proven, unchanged: no OFDM-FM mode has masks in either tier, and none of this has been on the air.** Everything above is one geometry, one deviation, one tap, one payload size, a static link, in simulation.
